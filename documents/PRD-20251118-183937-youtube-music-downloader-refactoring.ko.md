# 제품 요구사항 명세서 (PRD)
# YouTube Music Downloader - 전면 리팩토링 프로젝트

**문서 버전:** 1.0
**작성일:** 2025-11-18
**상태:** 초안 (Draft)
**담당자:** 개발팀

## 경영진 요약 (Executive Summary)

본 PRD는 YouTube Music Downloader 프로젝트의 아키텍처를 현대화하고, 유지보수성을 향상시키며, 보안을 강화하고, 2025년 Python 웹 애플리케이션 업계 모범 사례에 부합하도록 하는 전면적인 리팩토링 계획을 제시합니다. 이 리팩토링은 현재 Flask 기반 프로토타입을 현대적인 아키텍처 패턴, 의존성 관리 및 개발 관행을 사용하는 프로덕션 준비 애플리케이션으로 전환할 것입니다.

---

## 1. 개요 (Overview)

### 1.1 프로젝트 배경

YouTube Music Downloader는 사용자가 YouTube 동영상을 검색하고 다운로드하여 메타데이터(제목, 아티스트, 썸네일)가 포함된 MP3 형식으로 변환할 수 있는 풀스택 웹 애플리케이션입니다. 현재 애플리케이션은 다음을 사용합니다:

- **백엔드:** yt-dlp를 사용하는 Flask REST API
- **프론트엔드:** Radix UI 컴포넌트를 사용하는 React TypeScript
- **아키텍처:** pnpm workspaces를 사용하는 모노레포
- **배포:** Docker 컨테이너화

애플리케이션은 핵심 사용 사례에 대해 올바르게 작동하지만, 코드베이스에는 프로덕션 배포를 방해하는 상당한 기술 부채, 아키텍처 불일치 및 보안 취약점이 있습니다.

### 1.2 리팩토링 목적

리팩토링 계획의 목표는 다음과 같습니다:

1. **기술 스택 현대화** - 2025년 모범 사례 활용
2. **코드 품질 향상** - 더 나은 아키텍처와 패턴 적용
3. **보안 강화** - 식별된 취약점 해결
4. **유지보수성 증가** - 적절한 오류 처리 및 로깅 구현
5. **성능 최적화** - 아키텍처 병목 현상 해결
6. **확장성 확보** - 향후 성장 및 기능 추가 대비

### 1.3 전략적 정렬

본 리팩토링은 다음 전략적 목표를 지원합니다:

- **프로덕션 준비:** 프로토타입을 배포 가능한 애플리케이션으로 전환
- **기술적 우수성:** 최고 수준의 개발 관행 확립
- **사용자 경험:** 안정성 및 응답성 향상
- **개발자 경험:** 유지보수 가능하고 잘 문서화된 코드베이스 생성
- **미래 대비:** 고급 기능을 위한 기반 구축

## 2. 문제 정의 (Problem Statement)

### 2.1 중대한 문제점

현재 구현에는 몇 가지 중대한 아키텍처 및 코드 품질 문제가 있습니다:

#### 2.1.1 잘못된 Async/Await 사용
Flask 라우트가 `async`로 데코레이트되어 있지만 적절한 `await` 사용 없이 동기 코드를 실행합니다. 이는 진정한 비동기 프로그래밍의 이점을 활용하지 못하는 오해의 소지가 있는 코드를 만듭니다.

**영향:** 성능 저하, 개발자 혼란, 잘못된 동시성 모델

#### 2.1.2 스레드 안전성 위반
전역 가변 상태(YDL_OPTS 딕셔너리)가 동기화 없이 여러 스레드에 의해 런타임에 수정되어 동시 다운로드 시나리오에서 잠재적인 경쟁 조건을 생성합니다.

**영향:** 데이터 손상, 예측 불가능한 동작, 디버깅 어려운 오류

#### 2.1.3 취약한 YouTube 통합
검색 기능이 YouTube HTML을 스크래핑하고 임베디드 JavaScript 데이터(ytInitialData)를 파싱하므로 YouTube가 UI 구조를 업데이트할 때마다 중단됩니다.

**영향:** 서비스 중단, 유지보수 부담, 신뢰할 수 없는 검색 기능

#### 2.1.4 오류 처리 누락
구조화된 로깅 프레임워크가 없고, 예외를 조용히 처리하며, 오류 추적이 부족하여 프로덕션 문제 디버깅이 거의 불가능합니다.

**영향:** 알 수 없는 오류, 낮은 관찰성, 어려운 문제 해결

#### 2.1.5 보안 취약점
- YouTube URL에 대한 입력 검증 없음
- 비디오 ID를 통한 경로 탐색 가능성
- 인증 또는 속도 제한 없음
- 접근 제어 없이 엔드포인트 노출
- 위생 처리되지 않은 비디오 제목 (XSS 위험)

**영향:** 보안 침해, 악용 가능성, 데이터 노출

### 2.2 중간 심각도 문제점

#### 2.2.1 성능 병목 현상
- 프론트엔드가 진행 상황 업데이트를 위해 60fps로 폴링 (과도한 CPU 사용)
- 검색 결과에 대한 캐싱 레이어 없음
- 모든 업데이트마다 비효율적인 진행 파일 I/O
- 고정된 스레드 풀을 가진 단일 서버 제한

**영향:** 낮은 리소스 활용, 확장성 제한

#### 2.2.2 상태 관리 복잡성
프론트엔드가 복잡한 리셋 로직과 setTimeout 우회 방법을 가진 세 가지 중복 상태 관리 레이어(Context + Reducer + TanStack Query)를 사용합니다.

**영향:** 어려운 디버깅, 유지보수 문제

#### 2.2.3 하드코딩된 구성
매직 넘버, 한국어 UI 텍스트, 하드코딩된 경로, 구성 파일 지원 없음.

**영향:** 비유연성, 국제화 장벽

#### 2.2.4 의존성 관리 문제
requirements.txt와 pyproject.toml 간 버전 충돌, 사용하지 않는 의존성, 더 이상 사용되지 않는 라이브러리(wget).

**영향:** 공급망 위험, 비대한 의존성

### 2.3 경미한 문제점

- 혼합 언어 주석 (한국어 + 영어)
- 누락된 docstring 및 타입 힌트
- 접근성 기능 없음 (ARIA 레이블)
- 일관되지 않은 코드 포맷팅
- 강한 결합 (UI가 서버 디렉터리로 빌드됨)
- 포괄적인 테스트 커버리지 누락
- CI/CD 파이프라인 없음

## 5. 기능 요구사항 (Functional Requirements)

### 5.1 핵심 리팩토링 요구사항

#### FR-1: 비동기 아키텍처 마이그레이션
**우선순위:** P0 (중대)

잘못된 async 사용이 있는 Flask에서 적절한 async/await 구현을 갖춘 FastAPI로 마이그레이션.

**수락 기준:**
- 모든 API 엔드포인트가 await와 함께 적절한 async def 사용
- HTTP 클라이언트 작업이 httpx 또는 aiohttp 사용
- 파일 I/O가 논블로킹 작업을 위해 aiofiles 사용
- 데이터베이스 작업(추가된 경우)이 async 드라이버 사용
- async 함수에 블로킹 작업 없음

#### FR-2: 클린 아키텍처 구현
**우선순위:** P0 (중대)

헥사고날/클린 아키텍처 원칙에 따라 코드베이스 재구조화.

**수락 기준:**
- 인프라로부터 도메인 로직 격리
- 명확한 분리: 프레젠테이션, 애플리케이션, 도메인, 인프라 레이어
- 모든 외부 의존성에 대한 의존성 주입
- 데이터 접근을 위한 리포지토리 패턴
- 비즈니스 로직을 위한 서비스 레이어

#### FR-3: 의존성 관리 현대화
**우선순위:** P0 (중대)

워크스페이스 지원을 갖춘 Python 의존성 관리를 위해 uv 채택.

**수락 기준:**
- 의존성에 대한 단일 진실 공급원
- 재현 가능한 빌드를 위한 uv.lock 파일
- 모노레포를 위한 워크스페이스 구성
- 패키지 간 버전 충돌 없음
- 사용하지 않는 의존성 제거

#### FR-4: 오류 처리 및 로깅
**우선순위:** P0 (중대)

포괄적인 오류 처리 및 구조화된 로깅 구현.

**수락 기준:**
- 컨텍스트가 포함된 구조화된 로깅 (요청 ID, 사용자 ID 등)
- 스택 트레이스를 사용한 오류 추적
- 모든 오류 유형에 대한 HTTP 예외 핸들러
- API 응답에서 사용자 친화적인 오류 메시지
- 로그 레벨 적절히 구성 (DEBUG, INFO, WARNING, ERROR)

#### FR-5: 입력 검증 및 보안
**우선순위:** P0 (중대)

포괄적인 입력 검증 및 보안 조치 추가.

**수락 기준:**
- 모든 요청/응답 검증을 위한 Pydantic 모델
- 정규식을 사용한 YouTube URL 검증
- 파일 작업에서 경로 탐색 방지
- 허용된 출처가 있는 CORS 구성
- 모든 엔드포인트에 대한 속도 제한
- 콘텐츠 보안 정책 헤더

#### FR-6: YouTube 통합 개선
**우선순위:** P1 (높음)

HTML 스크래핑을 yt-dlp의 내장 검색 API로 교체.

**수락 기준:**
- ytsearch: 접두사와 함께 yt-dlp extract_info 사용
- 기본 검색 실패 시 대체 메커니즘
- 검색 결과 캐싱 (5분 TTL)
- API 실패에 대한 적절한 오류 처리
- 검색 결과 페이지네이션 지원

#### FR-7: 성능 최적화
**우선순위:** P1 (높음)

프론트엔드 폴링 및 백엔드 작업 최적화.

**수락 기준:**
- 프론트엔드 폴링을 60 Hz에서 1 Hz로 감소
- 폴링을 위한 지수 백오프 구현

## 8. 가정 및 종속성 (Assumptions & Dependencies)

### 8.1 가정

1. **외부 서비스:**
   - YouTube는 API 키 없이도 계속 액세스 가능
   - yt-dlp는 계속 활발히 유지보수됨
   - FFmpeg는 계속 사용 가능하고 안정적임

2. **인프라:**
   - 개발 기기에 충분한 리소스 (최소 8GB RAM)
   - 안정적인 인터넷 연결
   - 컨테이너화된 개발을 위한 Docker 사용 가능

3. **팀:**
   - 개발팀이 Python 및 TypeScript 전문성 보유
   - 팀이 비동기 프로그래밍 개념에 익숙
   - 코드 리뷰 프로세스 확립

4. **타임라인:**
   - 리팩토링 기간 동안 경쟁 우선순위 프로젝트 없음
   - 전체 리팩토링 기간 동안 리소스 할당
   - 배포 전 테스트 시간 확보

### 8.2 종속성

1. **기술 종속성:**
   - YouTube 다운로드를 위한 yt-dlp 라이브러리
   - 오디오 변환을 위한 FFmpeg 바이너리
   - 프론트엔드 빌드를 위한 Node.js 및 pnpm
   - Python 의존성 관리를 위한 uv

2. **프로세스 종속성:**
   - 기능 브랜치가 있는 Git 버전 제어
   - 코드 리뷰 승인 프로세스
   - CI 파이프라인에서 자동화된 테스트
   - 프로덕션 전 테스트를 위한 스테이징 환경

3. **외부 종속성:**
   - YouTube 서비스 가용성
   - 패키지 레지스트리 가용성 (PyPI, npm)
   - 기본 이미지를 위한 Docker Hub
   - 리포지토리 호스팅을 위한 GitHub

4. **위험 종속성:**
   - YouTube가 인터페이스를 변경할 수 있음 (yt-dlp API 사용으로 완화)
   - yt-dlp가 브레이킹 체인지를 도입할 수 있음 (버전 고정으로 완화)
   - FFmpeg 취약점 (최신 안정 버전 사용으로 완화)

## 12. 수락 기준 (Acceptance Criteria)

리팩토링 프로젝트는 다음 경우 **완료 및 성공**으로 간주됩니다:

### 12.1 기능 기준
- ✅ 모든 기존 기능이 이전과 동일하게 작동 (회귀 없음)
- ✅ 검색이 HTML 스크래핑 대신 yt-dlp API 사용
- ✅ 다운로드 기능이 신뢰할 수 있음 (>95% 성공률)
- ✅ 진행 추적이 실시간으로 업데이트
- ✅ 파일 관리 (목록, 다운로드, 스트리밍)가 올바르게 작동

### 12.2 기술 기준
- ✅ 적절한 async/await와 함께 FastAPI 마이그레이션 완료
- ✅ 클린 아키텍처 구현 및 검증
- ✅ uv 워크스페이스 구성 및 작동
- ✅ 타입 커버리지 >95% (mypy strict 모드 통과)
- ✅ 테스트 커버리지 >80% (pytest-cov 리포트)
- ✅ 보안 스캔이 0개의 중대 취약점 표시
- ✅ 모든 NFR 목표 충족 (§7 참조)

### 12.3 품질 기준
- ✅ 코드가 0개의 오류로 모든 린터 통과 (Ruff, ESLint)
- ✅ CI 파이프라인에서 모든 테스트 통과
- ✅ Lighthouse 점수 >90 (성능, 접근성)
- ✅ API 문서 완료 (OpenAPI)
- ✅ 아키텍처 문서 완료 (ADR)
- ✅ 개발자 설정 가이드 완료

### 12.4 프로세스 기준
- ✅ 모든 10개 단계 완료 및 커밋
- ✅ Git 히스토리가 깨끗하고 잘 문서화됨
- ✅ 원격으로 코드 푸시 안 함 (제약에 따라)
- ✅ 최소 한 명의 다른 개발자가 모든 변경 사항 검토
